# Testing Standards

이 문서는 이 저장소의 테스트 작성/실행 규칙을 정의한다.
Claude Code, Codex를 포함한 모든 AI 에이전트와 사람 기여자에게 동일하게 적용된다.

## 기본 원칙

- 기능을 추가하거나 동작을 변경하면 테스트도 함께 추가·수정한다. 테스트 없는 동작 변경은 완료로 간주하지 않는다.
- 새 Service public 메서드에는 최소 한 개 이상의 직접적인 단위/통합 테스트가 있어야 한다. (이 프로젝트는 현재 Testcontainers 기반 통합 테스트로 Service 계층을 검증하는 방식을 따르고 있다 — `DocumentServiceIntegrationTest` 참조)
- 다음을 포함해서 테스트한다: 정상 케이스, 대표적인 실패 케이스, 경계값 또는 예외 상황.
- 버그를 수정할 때는 가능하면 재현 테스트를 먼저 추가해 실패를 확인한 뒤, 수정하여 통과시킨다.

## 무엇을 검증하는가

- 테스트는 구현 세부사항이 아니라 관찰 가능한 동작과 비즈니스 규칙을 검증한다. (예: "특정 private 메서드가 호출되었는가"가 아니라 "저장 후 조회 결과가 기대한 값인가")
- 트랜잭션 경계, 권한 검증, 상태 전이, 중복 처리 등 중요한 비즈니스 제약은 반드시 테스트로 보호한다.
- 테스트끼리 실행 순서에 의존하지 않는다. 각 테스트는 독립적으로 실행 가능해야 한다. (이 프로젝트는 `@Transactional` 테스트 클래스로 각 테스트 종료 시 자동 롤백하여 격리한다 — 이 패턴을 유지한다.)

## 비결정적 의존성 처리

- 외부 API, 시간, 난수, 파일 시스템, DB 등 비결정적 의존성은 가능한 한 격리하거나 대체한다.
- DB 의존 테스트는 이 프로젝트의 기존 관례를 따라 **Testcontainers**를 사용한다. (`pgvector/pgvector:pg16` 이미지, `@DynamicPropertySource`로 접속 정보 주입 — `DocumentServiceIntegrationTest` 참조)
- 순수 Mock DB나 H2 대체를 임의로 도입하지 않는다. pgvector 등 프로젝트 DB 고유 기능(vector 타입, `<->` 연산자)을 사용하는 코드는 실제 호환 이미지를 쓰는 Testcontainers로 검증해야 신뢰할 수 있다.
- 스키마는 Hibernate 자동 생성(`ddl-auto`)에 의존하지 않고 `src/test/resources/schema.sql`을 명시적으로 관리한다. (`spring.sql.init.mode=always`)

## 금지되는 패턴

- 테스트를 통과시키기 위해 운영 코드를 약화하지 않는다. (예: 검증 로직을 테스트 편의를 위해 제거)
- 의미 없는 assertion을 작성하지 않는다. (예: `assertThat(true).isTrue()`, 예외를 잡고 아무 검증도 하지 않는 패턴)
- 실패하는 테스트를 삭제, `@Disabled`, skip 처리로 회피하지 않는다. 실패 원인을 해결하거나, 정말 더 이상 유효하지 않은 테스트라면 그 이유를 명시하고 논의한다.
- Sleep 기반 타이밍 의존 테스트를 새로 추가하지 않는다. 필요한 경우 polling/awaitility 등 명시적 대기 방식을 사용한다.

## 명명 규칙

- 테스트 메서드명은 "조건-행위-결과"가 드러나도록 작성한다.
- 이 프로젝트는 한글 테스트명을 사용하는 기존 관례가 있다 (`벡터_검색_동작`, `유사도_순서_정렬`, `문서_저장_및_조회`). 이 관례를 유지하고, 이름만으로 시나리오가 파악되도록 구체적으로 작성한다.
  - 예: `저장된_문서가_없으면_검색_결과가_빈_리스트다`, `쿼리_벡터와_동일한_문서가_최상위로_반환된다`

## 실행

- 테스트 실행 명령은 [workflow.md](./workflow.md)의 "명령어" 절 참조.
- 특정 테스트만 우선 실행할 때: `./gradlew test --tests "<FQCN>"`
- 테스트 실행 시간이 과도하게 늘어나면(예: Testcontainers 이미지 최초 pull 등) 원인을 설명하고, 영향받는 범위의 테스트를 우선 실행한 뒤 전체 스위트를 이어서 실행한다.

## 통합 테스트 확장

- 새로운 DB 의존 기능을 추가할 때도 동일하게 Testcontainers 통합 테스트로 검증하는 기존 전략을 따른다.
- 별도의 성격(예: 클러스터 장애 조치 검증처럼 인프라 상태 전이를 다루는 테스트)을 도입할 때는, 먼저 이 문서의 원칙(격리, 결정성, 관찰 가능한 동작 검증)을 그대로 적용할 수 있는지 검토하고, 실행 시간이 긴 테스트는 별도 태스크/태그로 분리하는 것을 고려한다. (TODO: 필요 시점에 확정)
