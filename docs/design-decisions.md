# 설계 결정 사항

## DD-001. 원문 버전과 검색 노출 버전을 분리한다

### 결정

`documents.version`은 최신으로 작성된 원문 버전, `documents.current_search_version`은 현재 검색에 노출하는 마지막 정상 임베딩 버전으로 분리한다.

### 이유

새 원문이 저장된 직후 임베딩은 비동기로 수행된다. 두 버전을 하나로 관리하면 새 버전이 `PENDING`인 동안 이전 정상 벡터가 검색에서 사라지거나, 임베딩 실패 시 검색 가능한 벡터가 없어질 수 있다.

### 결과

v2 임베딩 중에는 v1을 검색하고, v2가 `EMBEDDED`가 된 짧은 트랜잭션에서만 검색 노출 버전을 v2로 교체한다.

## DD-002. 과거 버전은 수정·삭제하지 않고 새 버전으로 복원한다

### 결정

과거 v1을 복원해도 v1 행을 다시 활성화하지 않고, v1 원문을 복사한 새 v3를 생성한다.

### 이유

감사 이력의 불변성을 유지하고, 복원 행위 자체도 추적하기 위해서다. 복원된 원문도 현재 임베딩 모델로 다시 벡터화해야 하므로 새 버전이 적합하다.

### 결과

`v1 → v2 → 삭제 → v1 복원`은 `v1 → v2 → v3(내용은 v1)`이 된다.

## DD-003. 삭제는 논리 삭제로 처리한다

### 결정

`deleted_at`과 `DELETED` 상태를 사용하며, 청크·벡터·버전 이력은 즉시 물리 삭제하지 않는다.

### 이유

삭제 후 복원, 감사, 장애 분석을 지원해야 한다. 검색 SQL은 `deleted_at IS NULL` 조건으로 삭제 문서를 즉시 비노출 처리한다.

### 향후 보완

보관 기한이 지난 이력을 비동기 정리하는 정책을 추가한다.

## DD-004. 사용자 수정에는 비관 락과 expectedVersion을 함께 사용한다

### 결정

수정·삭제·복원 시 `documents` 행을 `PESSIMISTIC_WRITE`로 가져오고, 요청의 `expectedVersion`이 현재 버전과 같은지 확인한다.

### 이유

동시에 들어온 수정 요청이 같은 새 버전을 만들거나 이전 요청을 덮어쓰는 것을 방지한다. `expectedVersion` 불일치는 HTTP 409으로 반환해 클라이언트가 최신 상태를 다시 읽도록 한다.

### 트레이드오프와 향후 보완

현재는 명확한 정합성을 우선해 조회 후 갱신한다. 고빈도 수정 부하가 확인되면 `UPDATE ... WHERE version = :expectedVersion RETURNING` 방식으로 왕복을 줄이는 것을 검토한다.

## DD-005. 청크는 버전별로 보존하고, 임베딩은 트랜잭션 밖에서 수행한다

### 결정

`document_chunks`는 `(document_id, document_version, chunk_index)`별로 보존한다. 모델 추론은 `EmbeddingWorker`에서 트랜잭션 밖에서 수행하고, 결과 저장·상태 전이·로그 기록만 짧은 트랜잭션으로 처리한다.

### 이유

느린 모델 추론 동안 DB 트랜잭션과 락을 유지하면 장애 시 롤백 범위와 복구 비용이 커진다. 버전별 청크를 남기면 특정 버전의 처리·감사·복원이 가능하다.

## DD-006. 내용 해시는 전역 중복 제거 키로 사용하지 않는다

### 결정

생성 멱등성은 `idempotency_key`만 사용하고, `content_hash`는 버전 식별·변경 감지용 메타데이터로 유지한다.

### 이유

서로 다른 소유자의 동일 본문을 전역 해시 기준으로 하나의 문서로 합치면 문서 소유권과 검색 권한 경계가 깨질 수 있다.

## DD-007. 작업 점유는 Outbox 행에서 원자적으로 수행한다

### 결정

`ingestion_tasks`의 `PENDING` 작업을 `FOR UPDATE SKIP LOCKED`로 조회하고, 같은 트랜잭션에서 `PROCESSING`으로 전이한다.

### 결과

여러 애플리케이션 인스턴스가 동시에 폴링해도 한 트랜잭션만 작업을 점유한다. 느린 모델 추론은 점유 트랜잭션 밖에서 실행한다.

## DD-008. 감사 이력과 작업 점유 상태를 분리한다

### 결정

`ingestion_log`는 `CREATED`·`EMBEDDED`·`FAILED` 같은 감사 이력을 유지하고, 워커 점유 상태는 버전당 하나인 `ingestion_tasks` outbox 행에 둔다.

### 이유

감사 로그 행을 `PENDING → PROCESSING → EMBEDDED`로 갱신하면 원래 발생 사실과 처리 상태가 섞인다. 반대로 문서 버전별 작업 행은 `FOR UPDATE SKIP LOCKED`로 짧게 점유·전이하기 적합하다.

### 결과

여러 인스턴스가 동시에 폴링해도 한 트랜잭션만 작업 행을 `PROCESSING`으로 바꾼다. 느린 모델 추론은 점유 트랜잭션이 끝난 뒤 실행하므로 DB 락을 오래 잡지 않는다.

## DD-009. 일시적 임베딩 실패는 지연 재시도하고, 새 버전은 전체 완료 후에만 검색에 노출한다

### 결정

`ingestion_tasks`에 시도 횟수, 다음 실행 시각, 마지막 오류를 둔다. 실패한 작업은 최대 시도 횟수 전까지 backoff 후 `PENDING`으로 되돌리고, 최대 횟수에 도달했을 때만 최종 `FAILED`로 전이한다.

청크 임베딩은 배치마다 저장하되 `completeEmbedding()` 트랜잭션에서 미임베딩 청크가 없는지 확인한 뒤에만 `current_search_version`을 갱신한다.

### 이유

일시적인 모델·네트워크 오류 때문에 즉시 최종 실패로 끝내면 운영자가 수동으로 개입해야 한다. 반대로 일부 청크만 새 버전으로 검색에 노출하면 한 문서의 서로 다른 버전이 섞일 수 있다.

### 결과

재시도 시 `embedding IS NULL`인 청크만 다시 추론한다. 새 버전 처리 중이거나 최종 실패해도 이전 `current_search_version`은 유지되어 마지막 정상 검색 결과를 제공한다. 수동 재처리는 별도 단계로 남긴다.

## DD-010. PROCESSING 작업은 만료 가능한 lease로 점유한다

### 결정

작업을 claim할 때 인스턴스별 worker 식별자와 2분 만료 시각을 기록한다. 임베딩 청크 배치의 추론 전후 heartbeat로 lease를 연장하고, 30초 주기의 회수기는 만료 작업에 일반 임베딩 실패와 같은 재시도 상한·backoff를 적용한다.

### 이유

추론은 DB 트랜잭션 밖에서 실행하므로 프로세스 종료·네트워크 단절 뒤 `PROCESSING` 행이 영구히 남을 수 있다. 반대로 단순 시간 기반 회수만 쓰면 느린 기존 워커가 새 워커의 결과를 덮어쓸 위험이 있다.

### 결과

heartbeat·완료·실패 전이는 현재 `claimed_by`와 일치하는 경우에만 적용한다. 회수기는 `PROCESSING`이면서 `lease_expires_at`이 지난 행을 잠근 뒤 backoff 시각으로 `PENDING` 전이하고, 상한에 도달하면 문서·버전·작업을 최종 `FAILED`로 전이한다. 만료된 옛 워커는 뒤늦게 완료되어도 검색 노출 버전을 바꾸지 못한다. 이미 저장된 청크 임베딩은 유지하므로 회수 뒤에는 `embedding IS NULL`인 청크만 다시 처리한다.

## DD-011. 파일 원본은 저장하지 않고 버전별 메타데이터와 추출 원문만 보관한다

### 결정

PDF와 UTF-8 TXT 파일을 요청 수명 안에서 텍스트로 추출해 기존 원문·청크·Outbox 트랜잭션에 연결한다. 원본 파일 바이트는 DB나 로컬 디스크에 영속 저장하지 않고, `document_versions`에 파일명·검증 MIME 타입·크기·SHA-256만 저장한다.

### 이유

대회 과제의 핵심은 파일 보관소가 아니라 OpenSQL 안에서 원문 버전과 벡터를 정합하게 동기화하는 것이다. 파일 바이너리 저장을 함께 도입하면 보관 위치, 접근 제어, 수명 주기, 백업 정책이 별도 과제가 된다. 입력 형식은 버전마다 달라질 수 있으므로 파일 메타데이터는 현재 문서 행이 아닌 버전 이력에 둔다.

### 안전 경계

파일 크기는 10 MiB로 제한하고, 확장자·MIME·PDF 헤더를 함께 확인한다. PDF는 암호화·손상·텍스트 없음, TXT는 UTF-8 디코딩 실패·빈 내용을 거절한다. 파서 예외 원문은 API 응답이나 DB 감사 이력에 저장하지 않는다.
